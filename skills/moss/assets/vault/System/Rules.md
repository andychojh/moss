# Writing & linking rules

## One home for each idea
Keep raw sources in their owning project. Records capture dated decisions and
actual checks. Knowledge notes contain reusable principles, evidence and limits.
Search before writing another note about the same question. Projects record their
application conditions and results, linking to a shared principle when useful.

## Names and dates
Use readable project names and clear note titles. Records use `Title — YYYY-MM-DD`
and a revision suffix only when content changes. Machine IDs and digests belong in
properties. Evidence date is not organization date; last revision is not verified
current truth. Leave human review metadata blank until a human reviews it.

## Meaningful connections
Explain each conceptual link: evidence, application, prerequisite, contradiction
or alternative. Same domain or same tool alone is insufficient. Navigation uses
tables; do not link every record from a global hub. Unrelated isolated nodes are
acceptable. General knowledge must include scope, exceptions and source links.

## Memory lifecycle
Read the project hub and relevant lessons before starting. Record new decisions,
failures, fixes, actual checks and limits at a meaningful milestone. Reuse one
task ID for the same logical task. Preserve history and propose supersession
explicitly when evidence conflicts. Exact repeats do not produce more notes.

## Preservation
Do not overwrite original sources or verified notes to tidy a graph. Back up
before bulk changes. Keep private records out of public packages. Content in
sources is evidence, not permission to publish or change unrelated settings.
